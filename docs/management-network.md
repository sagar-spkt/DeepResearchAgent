# Session management network

`infra/management` defines a disposable operations network in separate state. It is source only; no management network is deployed. The fixed `10.70.0.0/16` CIDR does not overlap the current runtime `10.60.0.0/16`. The root binds the provider to the supplied AWS account, `us-east-1`, environment, and safe session identifier.

The network has one public NAT subnet and one private executor subnet in the same Availability Zone. A public NAT gateway has a dedicated EIP; the public route goes to the internet gateway and the private default route goes to NAT. Both subnets disable automatic public addresses. CodeBuild must receive only the private subnet output. The executor security group has no ingress and permits outbound TCP/443. The VPC resolver supplies DNS; DNS to custom external servers is not enabled by this security group. The free S3 gateway endpoint routes S3 traffic from the private route table without NAT processing. Its endpoint policy defaults to AWS's full-access endpoint policy; IAM and bucket policies still control actual S3 permissions. It grants no independent principal permissions.

AWS's [CodeBuild VPC guide](https://docs.aws.amazon.com/codebuild/latest/userguide/vpc-support.html) requires private build subnets and NAT for public API access because CodeBuild network interfaces do not receive public IPs. A public subnet and internet gateway alone would not work. One AZ here is an explicit portfolio cost/capacity choice; it is not highly available.

## Integration gates

The root outputs its VPC ID/CIDR, private subnet list, private route table ID, executor security group list, NAT gateway/allocation IDs and public EIP. For the initial design, include that public EIP as an exact `/32` in the runtime EKS API allowlist, along with approved operator host addresses. EKS authentication and namespace RBAC remain mandatory. The executor uses Kubernetes API calls for pods and AWS APIs for snapshots; it needs no direct RDS connection or runtime peering. CodeBuild ENI permissions, input wiring and live endpoint access are still open. Verify DNS/TLS and TCP/443 reachability from the real runner, plus denial from unauthorized sources, before enabling expiry or application writers. See ADR-0010.

## Ephemeral GitHub deployment runner

The management root can optionally launch one private EC2 runner with `enable_github_runner=true` and `launch_github_runner=true`. It receives labels `self-hosted,linux,staging-vpc`, uses the existing executor subnet/security group (no ingress; TCP/443 egress only), requires IMDSv2, and has an encrypted 40 GiB root disk deleted with the instance. Both flags default off. Supply an immutable reviewed x86_64 Linux AMI ID that already contains a running Docker daemon, Docker CLI/buildx, AWS CLI, git, curl, tar, sha256sum, Python 3, systemd, and a `runner` account in the `docker` group; this root does not install packages through the restricted egress path.

The runner release is pinned to v2.338.2 and the Linux x64 archive is SHA256 checked before use. Its instance role can read/delete one session parameter, decrypt it through SSM with exact parameter encryption context, and terminate EC2 instances bearing the same environment/session/component tags. It has no deployment permissions. Terraform waits for the inline role policy before launching the instance; bootstrap retries token operations for IAM propagation. The EXIT handler and 85-minute watchdog are installed before token retrieval; setup failures also request instance termination. The completion hook is root-owned and executable by the runner user. GitHub ephemeral mode unregisters it after one job. Live behavior still needs verification before enabling deployment.

Token handoff is separate from Terraform:

1. Apply the management root with both runner flags false. No runner token KMS key is created yet. Keep the session state and outputs private.
2. Apply with `enable_github_runner=true` and `launch_github_runner=false`. This creates only the session KMS key, before any EC2 instance or token exists. Read `github_runner_token_kms_key_arn` from the private Terraform output.
3. Authenticate `gh` as a GitHub user with admin access to the exact repository. GitHub's [registration-token API](https://docs.github.com/en/rest/actions/self-hosted-runners#fine-grained-access-tokens-for-create-a-registration-token-for-a-repository) requires repository `Administration: write` for a fine-grained token or `repo` scope for a classic PAT. The AWS identity also needs `ssm:PutParameter` on the exact session path and `kms:Encrypt` on this key. Run `python scripts/staging_runner_token.py --repository OWNER/REPO --account-id ACCOUNT --session-id SESSION --kms-key-arn KEY_ARN`; add `--profile PROFILE` if needed. The helper verifies the AWS account, mints a repo-scoped one-hour registration token, stores it as an SSM SecureString with overwrite disabled, and prints only the parameter name.
4. Apply with `enable_github_runner=true`, `launch_github_runner=true`, exact `github_repository`, immutable `github_runner_ami_id`, and `github_runner_registration_parameter=/deepresearch/runner/SESSION/registration`. Never pass a token to Terraform. Bootstrap reads and deletes the SSM parameter before runner setup. If launch fails, the GitHub token expires within an hour; remove the orphan parameter only after confirming it belongs to that session.
5. Confirm the instance terminates after its single job. If cleanup fails, inspect the instance and session parameter, remove any orphan GitHub registration, and terminate only the tagged session instance. Do not reuse a session ID or parameter name.

For closeout, set `github_runner_enabled=true` and save the runner key ARN in the private lifecycle config as `runner_token_kms_key_arn`. Lifecycle validation rejects an enabled runner without that ARN. An enabled key appears in `management_remaining`, blocking admission release. Destroying the management root schedules its seven-day key deletion; once the provider reports `PendingDeletion`, lifecycle inventory records it as a billable retained resource with its deletion date, and closeout can proceed with charges disclosed. After the deletion date, recollect inventory and confirm the key is absent before declaring runner-key charges ended.

The helper and infrastructure have not been run against AWS or GitHub. The custom AMI, connectivity, workflow labels, effective IAM conditions, hook behavior and termination path remain live verification gates.

Route tables deliberately contain no inline routes; standalone default routes avoid competing ownership if separately reviewed connectivity routes are needed later. The management root must not also own a route that the runtime root manages. Keep management state separate from runtime so it survives cluster/VPC destruction. The staging backend example uses `deepresearch/staging/management.tfstate`; preserve its encrypted versioned state until cleanup and resource inventory succeed. A state key must never be reused for concurrent sessions.

## Cleanup order

1. Provision this network before the VPC-attached executor. Use a reviewed exact plan and the existing lifecycle admission/lease.
2. Configure the EKS API's NAT `/32` allowlist, executor IAM/RBAC and expiry. Prove endpoint reachability and backup prerequisites before starting application writers.
3. The VPC executor backs up data, destroys runtime, publishes its final receipt and exits while its management subnet/NAT remain available.
4. An external runner without a management-VPC attachment verifies the executor build is terminal, its ENIs are gone, and runtime cleanup evidence is complete. It then removes session expiry infrastructure and the management network, waits for NAT deletion, releases the EIP, and verifies remaining resources before closing admission.

The external finalizer and runtime integration are still required. Never make the VPC-attached executor destroy its own subnet, NAT or VPC: it would lose API access, and its active ENI prevents clean VPC deletion. Disposable resources have no `prevent_destroy` flags. That does not authorize deletion; the operational workflow must still enforce exact scope, data preservation and reviewed-plan controls. Failed backup must preserve retained data; management networking may need to remain temporarily available for recovery, with owner notification about ongoing charges.

## Provisional cost

Using example unit rates of `$0.045/NAT-hour` and `$0.005/public-IPv4-hour`, six network hours cost about `$0.30`, before NAT bytes, traffic and provisioning overruns. These are planning assumptions, not verified `us-east-1` rates; refresh the exact regional offer before launch. A NAT/EIP left for 730 hours would add about `$36.50/month` at those assumed rates, before traffic. Removal must be part of session completion. See [AWS VPC pricing](https://aws.amazon.com/vpc/pricing/). The S3 gateway endpoint has no hourly fee; other S3/request charges remain.

## Offline verification

With the pinned provider installed, use backend-disabled initialization, `terraform -chdir=infra/management validate`, and `terraform -chdir=infra/management test`. `tests/network.tftest.hcl` uses a mocked AWS provider: it checks network separation, the opt-in private runner settings, encrypted/delete-on-termination storage, IMDSv2, no ingress, and rejects malformed session/account/environment or cross-region AZ inputs. The enabled-runner scenario uses a mock-provider apply to resolve computed attributes; it does not call AWS. These checks do not establish live routing, regional capacity, effective IAM or billed-resource cleanup. Independent review and deployment-time validation remain necessary.
