# Expiry executor Kubernetes access

The expiry root creates a `STANDARD` EKS access entry for the exact CodeBuild executor role and environment cluster. It maps that role to `deepresearch:<environment>:expiry` and grants only `eks:DescribeCluster` for the cluster ARN. It attaches no EKS managed cluster-access policy and does not change the operator's administrator role.

`scripts/lifecycle/eks_access.py` exposes the pure `expiry_rbac(environment)` function. It returns a Kubernetes `List` containing a namespaced Role and RoleBinding for namespace `research`; it calls no service and applies nothing. An authorized operator must review and install those manifests through the exact cluster context before the expiry schedule is enabled. The namespace must already exist. Authentication without the RoleBinding is insufficient for backup/shutdown, and this source is not a live authorization check.

The Role permits reads and scaling of only the five named application/Langfuse deployments, pod reads/listing to verify quiescence, exec only into the two named ClickHouse/Valkey StatefulSet pods, and reads/list/watch/deletion of only the two application ingress names. Ingress list/watch is resource-name constrained: clients must supply a matching `metadata.name` field selector, as `kubectl delete --wait` does; listing all ingresses is not authorized. `kubectl cp` uses exec into Valkey; neither general pod exec nor Secret API access is granted. Pod listing includes metadata for all pods in `research` because the adapter checks that no writer remains. RBAC cannot constrain commands within an allowed exec request: this executor can read data and mounted credentials in those two backup pods and must remain a trusted operations identity.

EKS API endpoint networking, CodeBuild network/ENI permissions, AWS backup/destruction/state policies, immutable runner/artifacts, client credentials, and application restore remain separate gates. The access entry is in expiry state because it belongs to the session executor; deleting its runtime cluster removes cluster-side access. Recreating the runtime requires refreshing/reapplying the corresponding entry and RoleBinding before expiry can run again. Do not delete an executor principal without removing its access entry first. Retained executor resources still require inventory and explicit cleanup.

Before deployment acceptance, use the real executor identity to verify named scaling, backup pod exec/cp, quiescence listing, and ingress deletion; verify denial for other namespaces, arbitrary pod exec, Secret reads, RBAC writes, and operator/cluster administration. No live Kubernetes authorization or AWS mutation has been performed for this source change.

References: [EKS access entries and Kubernetes groups](https://docs.aws.amazon.com/eks/latest/userguide/creating-access-entries.html), [Kubernetes RBAC resource names and subresources](https://kubernetes.io/docs/reference/access-authn-authz/rbac/).
